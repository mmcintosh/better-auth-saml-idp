# Example: SAML IdP with tenants on CharDB (experimental)

> **Experimental.** [CharDB](https://github.com/zpg6/chardb) is at 0.1: read its [Plan ahead](https://docs.chardb.dev/plan-ahead) before storing data you can't recreate. This example is outside better-auth-saml-idp's [versioning promises](../../docs/guide/versioning.md): it may change or break with any CharDB release. The plugin itself is not experimental here; CharDB is.
>
> **Tested with:** better-auth-saml-idp 1.1.0, Better Auth 1.7.6, and CharDB 0.1.0 built from [a Better Auth 1.7 branch](https://github.com/mmcintosh/chardb/tree/chore/better-auth-1.7) (commit `3329fa5`, in `../../vendor/`), proposed upstream in [zpg6/chardb#38](https://github.com/zpg6/chardb/pull/38). Published CharDB 0.1.0 requires Better Auth 1.6, and the plugin requires 1.7.5 or later. Once CharDB publishes a release for Better Auth 1.7, this example moves to it.

A [CharDB](https://docs.chardb.dev) app (Better Auth on Durable Objects, generated by `chardb init`) that is also a **multi-tenant SAML identity provider**. All of the plugin's tables live in CharDB's Catalog, created by CharDB's own migrations. It shows:
- the root IdP, at `/api/auth/saml2/idp` (metadata, SSO, SLO);
- **tenants**: an organization made its own IdP, with its own entity ID, metadata, SSO/SLO URLs and **signing key** (generated per tenant, stored encrypted with `BETTER_AUTH_SECRET`, rotated in three steps);
- **delegation**: the organization's owners and admins may manage its SPs through the registry API;
- SP-initiated sign-in through a tenant, replay protection, and a user outside the organization refused.

What was added to the generated app:

| File | What |
| --- | --- |
| `src/saml.ts` | The plugin's configuration: `tenants: { enabled: true, keys: "per-tenant", delegation: {} }`, the registry, Single Logout and the audit log |
| `src/auth.ts` | Sign-in by verified email (the IdP only asserts verified addresses), organization invitations, a dev-only mailbox, Better Auth's base URL, and the plugin |
| `src/background.ts` | Better Auth's background work (the plugin's events and audit rows) under the Worker's `waitUntil`; without it they're dropped after the response |
| `src/demo.ts` | The UI's server routes, and a **demo SP** (`/demo-sp`) to try sign-ins in the browser |
| `src/sign-in.ts`, `src/worker.ts` | The IdP's login page at `/sign-in`, and `/dev/mailbox` |
| `src/web/` | The UI (below), replacing the generated chat demo |
| `src/migrations/v2.*` | Generated by CharDB: the organization plugin's tables and the plugin's |
| `test/saml.test.ts` | The whole flow inside workerd |
| `scripts/dev-keys.mjs` | `bun run keys`: a throwaway key pair and local settings in `.dev.vars` |

The generated `messages` table and its test stay (CharDB's baseline); the UI no longer shows it.

## The UI

| Page | What |
| --- | --- |
| Overview | The root IdP's entity ID, SSO/SLO and metadata URLs, the tenants, and a walkthrough |
| Organizations | Create organizations; members and roles; invite a colleague as *admin* (manages the tenant's SPs) or *member* (signs in) |
| Tenants | Make an organization a tenant; its URLs; its keys: rotate, activate (after 24 hours, or forced), retire; enable, disable, delete |
| Service providers | Per tenant (or all, for host admins): add from metadata XML or JSON, edit, enable, disable, delete |
| Try it | Register the demo SP in a tenant, then sign in to it, SP- or IdP-initiated |
| Activity | The audit log: sign-ins, refusals, logouts, and every change to tenants, keys and SPs |

Host admins (`SAML_REGISTRY_ADMINS`) see everything. An organization's owners and admins see their own tenants (read-only) and manage their SPs and see their activity (delegation). The demo SP shows the Response it receives, including which published certificate signed it; it does **not** verify the signature, which a real SP must.

## Run it locally

Bun 1.2.22 or newer and Node.js 22 or newer. From this folder (it installs with Bun, outside the repository's pnpm workspace):

```sh
bun install
bun run keys        # writes .dev.vars: a dev-only IdP key pair, BETTER_AUTH_URL, DEV_MAILBOX, SAML_REGISTRY_ADMINS
bun run typecheck
bun run test        # CharDB's generated test, and test/saml.test.ts
bun run dev         # the Worker on http://127.0.0.1:8787, the web app on http://127.0.0.1:5173
```

Open `http://127.0.0.1:5173` and create an account as `admin@example.test` (the default `SAML_REGISTRY_ADMINS`); with `DEV_MAILBOX` the verification link is offered on screen. Everything runs on that one origin: Vite passes `/api`, `/sign-in`, `/dev` and `/demo-sp` to the Worker, and `BETTER_AUTH_URL` is set to it, so the IdP is at `http://127.0.0.1:5173/api/auth/saml2/idp`.

The same through the API, signed in:

```sh
# an organization (you become its owner), then its tenant with a new signing key
POST /api/auth/organization/create        {"name":"Acme","slug":"acme"}
POST /api/auth/saml-idp/tenants/create     {"organizationId":"<id>","tenantKey":"acme"}
# its metadata, with its own certificate
GET  /api/auth/saml2/idp/metadata/acme
# an SP of the tenant
POST /api/auth/saml-idp/service-providers/create  {"serviceProvider":{"id":"acme-app","entityId":"…","acsUrls":["…"],"tenant":"<id>"}}
# key rotation: publish a next key, activate it (after 24 hours; "force": true for a leaked key), retire the old one
POST /api/auth/saml-idp/tenants/keys/rotate    {"organizationId":"<id>"}
POST /api/auth/saml-idp/tenants/keys/activate  {"organizationId":"<id>"}
POST /api/auth/saml-idp/tenants/keys/retire    {"organizationId":"<id>"}
```

The [multi-tenant guide](../../docs/guide/multi-tenant.md) has the whole API. `test/saml.test.ts` runs these steps.

## Changing the schema

CharDB's CLI reads `src/auth.ts` to generate migrations, and the plugin needs its settings when it's built, so run it with `.dev.vars`:

```sh
bun run migrations:generate --name add_something
```

Don't edit files under `src/migrations` after deploying (CharDB's rule).

## Notes

- **Background work needs `waitUntil`.** The plugin writes its events and audit rows in the background (Better Auth's `backgroundTasks`). On Workers that must run under `waitUntil`, or the runtime drops it once the response is sent; CharDB doesn't set it, so `src/background.ts` does. `test/saml.test.ts` fails without it.
- **Better Auth's base URL** is set to `BETTER_AUTH_URL` too, so its own links (verification, invitations) use the app's origin rather than the Worker's behind the dev proxy.
- **Configuration comes from the Worker's variables and secrets** (`process.env` under `nodejs_compat`): `BETTER_AUTH_URL` (this Worker's origin; it pins the entity IDs, never a Host header), `SAML_IDP_PRIVATE_KEY`, `SAML_IDP_CERT` and `SAML_REGISTRY_ADMINS`. The Worker refuses to start without the first three.
- **Replay protection** (single-use AuthnRequest IDs and pending requests) is a UNIQUE insert through CharDB's Catalog Durable Object. It relies on Durable Object RPC being delivered at most once, which is the platform's default for these calls (CharDB doesn't mark them retryable). A retried insert would see its own first write and refuse a genuine request as a replay: it fails closed.
- **A log line during the tests:** `uncaught exception … UNIQUE constraint failed: samlIdpSeenRequest.key`. That is the replay test's duplicate insert: CharDB's Catalog passes the SQLite error on unwrapped, and workerd logs any error leaving a Durable Object call. The plugin catches it and answers `DUPLICATE_REQUEST_ID`, which the test checks.
- **Wrangler's configuration:** the scripts pass `--config wrangler.toml`, because inside this repository Wrangler would otherwise find the root's `wrangler.jsonc` first.
- **Deploying isn't covered yet.** CharDB's `deploy:bootstrap` uploads only its own two secrets, and this Worker needs the SAML values before it starts. The rest of CharDB's generated README (deployment, recovery) is in the [CharDB docs](https://docs.chardb.dev).
